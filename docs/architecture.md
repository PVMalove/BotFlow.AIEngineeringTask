# Архитектура BotFlow

## Границы первой версии

Приоритет — быстро довести до демонстрации полный путь Telegram → задача →
двуязычная доска. Три контекста и выбранные транспорты сохраняются; надёжность
ограничена базовыми повторами, дедупликацией, ошибкой/replay одного задания
и обычным рестартом. Расширенные эксплуатационные гарантии отложены
[ADR-0021](adr/0021-proportionate-reliability.md).

## Контексты и владение данными

| Контекст | Владеет | Внешний интерфейс |
| --- | --- | --- |
| Identity | учётные записи, заявки, допуск/роли, коды входа, сессии/отзыв | пользовательский REST и ограниченный внутренний HTTP |
| Tasks | задачи, авторство, статусы, версии, inbox/outbox доски | REST, WebSocket, RabbitMQ commands/results |
| Automation | Telegram updates, задания, транскрипции, уведомления, метаданные аудио | Telegram, RabbitMQ, Redis Streams, S3 |

Отдельная PostgreSQL на контекст. API/worker внутри одного сервиса используют
его модель и БД; межсервисные отношения передаются ID, без SQL JOIN между БД.
Отображаемое имя отделено от устойчивого ID автора. Redis и RabbitMQ являются
транспортами, PostgreSQL — источником состояния обработки и дедупликации.

## Внутренние слои

- `domain`: сущности, значения и инварианты, без ORM/HTTP/DI импортов.
- `application`: команды/запросы и порты; зависимости передаются конструкторами.
- `infrastructure`: репозитории, UoW, outbox/inbox, брокеры, S3 и Telegram/STT адаптеры.
- `api`: HTTP-маршруты и схемы; `scripts/`: точки входа bot, worker и bootstrap.
- `api/containers.py`: composition root сервиса, lifecycle ресурсов.
- `contracts`: независимые от фреймворка View на frozen dataclasses для BFF.
- `core`: кросс-срезная политика сервиса; `common`: локальные утилиты.

Слои лежат прямо в `backend/services/<service>/src/`, без промежуточного
пакета с именем сервиса. Каждый сервис запускается с собственным `src` в пути
импортов; исходники других сервисов в этот процесс не подключаются. CLI-точки
входа находятся в `scripts/`, тесты разделены на `unit/`, `integration/`, `e2e/`,
`performance/`. Рядом с `src/` предусмотрены `k8s/`, `docs/` и `ci/`.

CQRS локальный, без отдельной read DB/универсального dispatcher. UoW коммитит
бизнес-изменение и outbox/inbox вместе; репозитории не коммитят. Сессии БД
изолированы по операции, rollback — по умолчанию. Длительный Whisper не держит
DB-транзакцию и не блокирует ingress, уведомления или heartbeat брокера.

Референс — [ProductsFlow](https://github.com/PVMalove/ProductsFlow). Подходы
адаптированы к контекстам BotFlow; наличие workers само по себе не определяет
границы сервисов. Компенсируемой бизнес-операции в текущем workflow нет,
поэтому отдельный координатор Saga не вводится.

## Создание и доставка

1. Бот проверяет текущий допуск через Identity, лимит и поддерживаемый вход.
2. Automation атомарно сохраняет сообщение и outbox; затем отвечает о приёме.
3. Текст формирует CreateTask без Whisper. Голос уходит через Redis Streams:
   worker скачивает файл по file_id, сохраняет MinIO-объект, распознаёт речь.
4. Automation сохраняет транскрипцию/checkpoint и CreateTask outbox. Команда
   доставляется RabbitMQ в Tasks.
5. Tasks в одной транзакции сохраняет inbox, задачу с уникальным источником
   и результат TaskCreated в outbox. Повтор не создаёт вторую задачу.
6. Automation принимает результат через inbox и сохраняет намерение уведомить;
   отправка выполняется через Redis Streams. Ошибка уведомления не удаляет задачу.
7. Tasks после commit выпускает сигнал доски через Redis Pub/Sub независимо
   от уведомления автора. WebSocket предлагает перечитать REST.

ACK consumer — после локального commit. RabbitMQ publisher использует confirms,
mandatory и обработку returns, сообщения/топология durable. Неоднозначная
публикация повторяется с устойчивой идентичностью. Consumer inbox и DB unique
ограничение обязательны; exactly-once для внешних эффектов не заявляется.

До трёх попыток операции с задержками 5/30 секунд и jitter. Постоянная ошибка
завершается сразу. Недоступная инфраструктура оставляет надёжно сохранённое
ожидание; счётчик/следующий запуск в PG не обнуляются рестартом. Ошибка/DLQ
видна оператору и повторяется CLI; broker DLQ не заменяет запись ошибки в PG.

При недоступном брокере вход сохраняется при работающих PG/Identity и наличии
места. При недоступном Automation PG offset не продвигается за несохранённый
update. Обычный рестарт обрабатывает сохранённые outbox/pending без второй задачи.
Полная потеря брокера/томов не покрывается гарантией автоматического восстановления
первой версии; отдельную систему сверки и массового replay не строим.

## Доступ и конкурентные изменения

Одна команда/доска. Допуск через заявку и решение admin; web login через код
Telegram. JWT RS256 хранится в HttpOnly cookie, приватный ключ только у Identity.
Срок JWT — 8 часов, код — 5 минут/одно использование; block отзывает все сессии,
unblock требует нового входа. Проверка подписи не заменяет актуальный допуск.

Каждый новый защищённый HTTP-запрос и WS-подключение/отправка проверяют Identity.
При его недоступности новая защищённая операция запрещается. Правомерно принятое
до block задание завершается, но итоговое уведомление о задаче подавляется.
Внутренние HTTP-вызовы используют отдельные сервисные ключи и ограниченные
операции; эти ключи не дают общих admin-прав. Внутренние маршруты не открываются
через frontend ingress. Секреты не передаются в URL/логи/JS bundle.

Автор/admin свободно меняет Pending / In Progress / Completed. PATCH передаёт
expected_version; сравнение и UPDATE атомарны. Stale всегда 409. При актуальной
версии no-op не увеличивает её. Потерянный ответ — перечитать карточку без
автоматического повторения команды.

## Панель и realtime

React SPA, Material UI, TanStack Query. Три колонки, явный переключатель статуса,
на узком экране вертикальное расположение. До 50 карточек/колонку, новая сверху,
история через «Показать ещё». Reconnect, focus и периодический refresh раз
в 30 секунд активной вкладки закрывают потерю Pub/Sub-сигнала. Сигнал во время
fetch не должен потеряться; старый ответ не перезаписывает свежую версию.

Веб-интерфейс на русском и армянском: «Русский / Հայերեն», выбор сохраняется
локально. Переводятся элементы UI и ошибки, а не текст задач. Светлая доска,
графит и золотистый акцент оформляются темой MUI под названием BotFlow.
Внешний брендинг не переносится. Подробности — [дизайн](frontend-design.md).

Один origin SPA/API/WS. Изменяющие операции защищаются от CSRF; WS проверяет
Origin. Локальный профиль открыт только через loopback; исключение Secure
для HTTP cookie не переносится во внешний профиль.

## Аудио, нагрузки и сохранность

Локальный официальный Whisper, RU/hy auto detect. Модель выбирается по смысловой
точности и скорости отдельно на обоих языках. Цель прогретого исправного пути:
ACK ≤2 секунд и задача на панели ≤60 секунд при пустой очереди/аудио ≤60 секунд.
Это цель, не результат измерения. Cold start и занятая очередь учитываются отдельно.

Лимит аудио — 60 секунд/5 MiB, один Whisper одновременно; голосовые незавершённые
задания 10/2, все задания 100/10 на систему/пользователя. Ограничения атомарны
в PG. Переполнение отклоняется до ACK, принятые задания не удаляются.

Веса модели — постоянный Docker-том, явная подготовка/проверка целостности;
worker готов после загрузки в память. Целевая политика хранения аудио успешной задачи —
7 дней. Автоматическая очистка аудио/успешной
истории и compaction outbox/inbox отложены; первая версия не обещает удаление
по расписанию. Исходные ID и данные для повтора сохраняются.

Постоянные Docker-тома обеспечивают сохранность при обычном down/up без
удаления volumes. Backup/restore трёх PostgreSQL и S3 остаётся дальнейшим
эксплуатационным улучшением, не обязательным критерием первой версии.
Потеря томов не покрывается обещанием восстановления. Секреты не публикуются.

## Docker и состояние каркаса

Образы backend собираются отдельно по сервисам из uv workspace, runtime —
Python 3.12 под непривилегированным пользователем. Frontend собирается Node 24
и раздаётся непривилегированным nginx. Образы инфраструктуры закреплены digest.
MinIO собирается из официального commit 9e49d5e7a648f00e26f2246f4dc28e6b07f8c84a:
старый образ референса недоступен, а upstream архивирован. Доступность исходника
не является доказательством безопасности или успешной сборки; build/S3-проверка
обязательны перед рабочим использованием.

Compose содержит постоянные тома, secret-файлы, инфраструктуру и HTTP-оболочки.
Профили `bootstrap`/`workers` показывают состав процессов. Сейчас эти точки
входа и Alembic env отказывают явно: бизнес-обработчики/metadata ещё отсутствуют.
HTTP liveness не является бизнес-readiness; `/health/ready` возвращает 503.
Whisper/PyTorch/ffmpeg и подготовка ключей RS256 подключаются после проверки
совместимости. Автоматического ложного успешного bootstrap нет.

Скрипт `make init` создаёт локальные credentials без перезаписи. Каталог
`.secrets` доступен только владельцу; файлы читаются назначенными контейнерами.
Bot token заполняется владельцем. Credentials другого проекта не переиспользуются.

## Проверки и дальнейшие границы

CI: статические проверки, целевые unit/integration, образы и изолированный
E2E основного пути. Обязательные проверки: повтор одного входа/команды без
двойной задачи, rollback и ACK после commit, ограниченный retry/ошибка/replay,
рестарт worker, права/409, S3 roundtrip, WS-resync и переключение RU/HY.
Интеграционные проверки используют реальные PG/Redis/RabbitMQ/MinIO;
Telegram/Whisper в CI заменяются на портах. Живая проверка отдельно подтверждает
Telegram и RU/hy корпус; тестовые подмены не доказывают качество распознавания.
Исчерпывающая fault-матрица, retention и restore не являются gate первой версии.

Полный QA пока не готов: бизнес-тесты и изолированное E2E окружение отсутствуют.
Пустые наборы не считаются успешными. Приложение не заявляет рабочие auth,
фоновые задания, HA или серверный CD на основании одного каркаса.

Состояния workflow, envelope сообщений, конкретные timeout/lease/reclaim,
rate limits, ключи/ротация, миграции и реальные тесты уточняются при реализации
в соответствии с [ADR](adr/). Принятые решения сохраняются независимо от
инструмента оркестрации разработки.
