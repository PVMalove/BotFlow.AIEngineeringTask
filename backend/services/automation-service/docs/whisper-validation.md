# Проверка локального Whisper на RU/hy (#4)

Ранняя проверка официального Whisper на реальной русской и армянской речи.
Она не запускает приложение и не измеряет Telegram, S3, очередь, создание задачи и панель.
Полный голосовой путь — #14 (см. раздел «Голосовой путь» в `docs/architecture.md`; там же
процесс `whisper-worker`, тайм-аут 120 с и порог зависшей записи 180 с), живая приёмка — #17.

**Статус (2026-10-22): живой прогон на шести записях владельца выполнен, модель и параметры
выбраны агентом по замерам по поручению владельца («самостоятельно определи настройки»).
Смысловая оценка — автоматическая эвристика, человеком не подтверждена; качество на hy низкое.
Критерии «подтверждение владельца» и «подходящая модель для hy» остаются открытыми.**

## Runtime

Официальный `openai-whisper==20250625`, `torch==2.14.1` (CPU-сборка с
`download.pytorch.org/whl/cpu`), `psutil==7.2.2` — optional extra `stt` сервиса
(`backend/services/automation-service/pyproject.toml`, закреплено в `backend/uv.lock`).
`make deps` extra не ставит. Устройство: **только CPU, fp32** (`fp16=False`);
GPU не проверялся и не обещается.

Образ — цель `stt-runtime` в `Dockerfile` сервиса: `python:3.12-slim-bookworm`
(тот же закреплённый digest, что у API), ffmpeg/ffprobe из Debian, пользователь
`botflow` (UID 10001), `/models` принадлежит ему. Образ `botflow-whisper-validation:local`,
собирается отдельным `docker-compose.whisper.yml` (проект `botflow-whisper`); он не требует
`.env`, секретов, БД, Redis и RabbitMQ и не наследует `COMPOSE_FILE`/`COMPOSE_PROFILES`.

Проверено при сборке на машине разработки (x86_64 Linux, Docker 29.9.1):

| Компонент | Версия |
| --- | --- |
| Python | 3.12.15 |
| openai-whisper | 20250625 |
| torch | 2.14.1+cpu (`cuda.is_available() == False`) |
| ffmpeg / ffprobe | 5.1.9-0+deb12u1 |
| Образ | `sha256:536aeeb3dbff…` (3.76 GB; ~0.9 GB из них `triton`, который тянет whisper и CPU не нужен) |

Идентичность образа и коммит каждый прогон `bench` записывает в результат сам
(`host.image_id`, `host.git_commit`, `host.git_dirty`).

## Команды

```bash
make whisper-build                        # образ stt-runtime; качает пакеты, нужна сеть
make whisper-prepare WHISPER_MODEL=turbo  # единственный шаг с сетью: turbo 1 617 941 637 байт (small — 483 617 219)
make whisper-verify  WHISPER_MODEL=turbo  # SHA-256 + загрузка в память; без сети, том read-only
make whisper-corpus-check                 # корпус из .local/whisper/corpus; read-only, без сети
make whisper-bench   WHISPER_MODEL=turbo  # весь протокол (по умолчанию turbo); результат в .local/whisper/results.json
```

Установка пакетов и загрузка весов — отдельное разрешение владельца; проверки
(`verify`, `corpus-check`, `bench`, `make test/check`) ничего не устанавливают и не скачивают.

### Веса и том

- Постоянный том по умолчанию `botflow_whisper_models` (совпадает с `whisper_models`
  основного Compose при проекте `botflow`). Для другого `COMPOSE_PROJECT_NAME` явно:
  `WHISPER_MODELS_VOLUME=<имя>`. `prepare` пишет в том, остальные команды монтируют его read-only.
- URL и SHA-256 берутся из закреплённой таблицы `TRUSTED_WEIGHTS` — копия `whisper._MODELS`
  версии 20250625 (SHA-256 — предпоследний сегмент URL). Таблица содержит только
  мультиязычные `tiny`, `base`, `small`, `medium`, `large-v3`, `turbo`; варианты `.en` запрещены.
- Скачивание идёт в `<model>.pt.part`, проверяется и атомарно переименовывается; частичный
  или повреждённый файл не публикуется. Повторный `prepare` с валидным файлом ничего не качает.
- `verify`/`bench` загружают модель по проверенному **локальному пути**, не по имени, поэтому
  скрытая загрузка невозможна; контейнеры работают с `network_mode: none`.
- Проверено на реальном томе: `prepare` → `verify` в новом контейнере → повторный `verify`
  в ещё одном контейнере (оба успешны, загрузка в память ≈4 с); на отдельном временном пустом
  томе `WHISPER_MODELS_VOLUME=<tmp> make whisper-verify` завершается с ошибкой
  «weights … missing … run prepare» без сети (временный том затем удалён); запись в
  `/models` из read-only контейнера невозможна.

## Корпус

Владелец локально кладёт шесть настоящих записей и `manifest.json` в
`.local/whisper/corpus/` (каталог в `.gitignore`, в Git не попадает).
Аудио, эталоны и транскрипции не передаются облачным сервисам и не коммитятся.
Примерные id: `ru-10`, `ru-30`, `ru-60`, `hy-10`, `hy-30`, `hy-60`; имена и числа должны
встречаться в корпусе обоих языков; армянские эталоны подтверждает человек, понимающий язык.

Схема `manifest.json`:

| Поле | Значение |
| --- | --- |
| `samples` | ровно шесть записей: по три на `ru` и `hy` |
| `id` | уникальный непустой идентификатор, например `ru-10` |
| `language` | `ru` или `hy`; это только эталон, в модель язык не передаётся |
| `audio` | путь относительно каталога манифеста; выход за каталог (в том числе симлинком) запрещён |
| `reference_text` | непустой эталон владельца, Unicode |
| `expected_action`, `expected_object` | непустые строки |
| `expected_names`, `expected_numbers` | список строк (или одна строка); пустой список `[]` — явное «нет». В каждом языке хотя бы одна запись содержит имена и хотя бы одна — числа |

Длительность и размер берутся из файла (`ffprobe`, размер на диске); значения,
заявленные в манифесте, игнорируются. Жёсткие пределы: ≤ 61 секунды и ≤ 5 MiB, файл не пустой.
Лимит продукта — 60 секунд; лишняя секунда нужна только потому, что `ffprobe` у Opus-файла
«ровно 60 секунд» показывает 60.006 (кадры контейнера). Записывайте реальные «минутные» голосовые
не длиннее 60 секунд.
Для каждого языка длительности, отсортированные по возрастанию, должны попадать в окна
7–13 с (≈10), 25–35 с (≈30) и 50–61 с (≈60); верхний предел окна совпадает с жёстким пределом.

Искусственный пример записи (только иллюстрация схемы, не результат приёмки):

```json
{
  "samples": [
    {
      "id": "ru-10",
      "language": "ru",
      "audio": "ru-10.ogg",
      "reference_text": "Купить молоко до пятницы",
      "expected_action": "купить",
      "expected_object": "молоко",
      "expected_names": ["Анна"],
      "expected_numbers": ["5"]
    }
  ]
}
```

## Протокол `bench`

Один новый контейнер/процесс, одна модель, одна запись за раз, без сети:

1. `process_startup_seconds` — от создания процесса Python до начала работы скрипта
   (запуск самого контейнера Docker не входит).
2. `model_load_seconds` — `import whisper/torch` и чтение проверенного чекпоинта в память.
3. Проход 0: каждый из шести файлов один раз. Самый первый вызов — фаза `cold`
   (первое распознавание процесса), остальные — `first_pass`.
4. Три прогретых прохода (`warm`) по всем шести файлам в том же процессе (всего 4 вызова на файл).

Каждый вызов — весь `model.transcribe(...)`, включая декодирование аудио через ffmpeg и все
30-секундные окна; аудио не обрезается. Параметры (записываются в результат как
`parameters.decode`): `task="transcribe"`, `language=None` (автоопределение), `initial_prompt=None`,
`fp16=False`, `verbose=None` (без печати транскрипций), `temperature=0.0` (без температурного
fallback), `compression_ratio_threshold=2.4`, `logprob_threshold=-1.0`, `no_speech_threshold=0.6`,
`condition_on_previous_text=False`, `word_timestamps=False`. Значения `temperature`/
`condition_on_previous_text` выбраны по замерам (см. ниже); прогон `turbo-default` шёл со стандартными
`[0.0, 0.2, …, 1.0]` и `True`.
Эталонный язык и текст в модель не передаются. RTF = время вызова / измеренная длительность.

Холодный процесс **не** равен очищенному файловому кэшу ОС: чекпоинт и библиотеки могут
лежать в page cache хоста, поэтому `model_load_seconds` — это «новый процесс при тёплом кэше ОС».
Скачивание весов во времена не входит.

Память: на каждый вызов — пик RSS процесса **плюс дочерних процессов (ffmpeg)**, снятый
потоком-сэмплером (интервал 20 мс; процесс ffmpeg короче интервала может не попасть в выборку).
Дополнительно `memory.ru_maxrss_self_mib` / `ru_maxrss_children_mib` (пик за весь процесс; для
детей на Linux значение включает RSS форкнутого процесса до `exec`, поэтому оно завышено и
не является чистым RSS ffmpeg). RAM хоста (`ram_total_mib`, `ram_available_mib` до запуска),
лимиты и пик контейнера (`cgroup.memory_max_bytes`, `memory_peak_bytes` — cgroup v2,
учитывает page cache; `null` — лимита нет, `"unavailable"` — метрика недоступна), число потоков
torch, число доступных CPU и модель CPU — в `environment`/`parameters`. VRAM не измеряется (CPU).

Результат — один JSON (с транскрипциями, поэтому только локально) в
`.local/whisper/results.json`: по каждому `id` эталонный и определённый язык, длительность,
размер и SHA-256 файла, все исходные времена/RTF/пики памяти, ошибки, транскрипции;
максимум и среднее по прогретым вызовам. Launcher сохраняет его атомарно; перед запуском
старый файл удаляется, при сбое остаётся маркер `success: false`. `success` истинно, только
если для каждого из шести `id` выполнены все четыре вызова и ни один не пустой/не упал.
Пустая транскрипция — неуспех. Токены и окружение процесса в результат не попадают;
`stderr` содержит только технические ошибки без текста записей.

Если сравнивается другая модель, перед новым прогоном сохраните прежний результат под
именем кандидата (`mv .local/whisper/results.json .local/whisper/results-small.json`).

## Результаты живого прогона (2026-10-22)

Корпус владельца: `ru` 10.4/30.1/52.1 с, `hy` 11.8/30.5/55.2 с (WAV, проверка `corpus-check` пройдена).
Машина: Intel Core Ultra 5 125H, 18 доступных CPU, torch 14 потоков, 31.5 GiB RAM (≈8.6 GiB
свободно), без лимитов контейнера. **Во время всех прогонов хост был нагружен (load average ≈ 12–14
на 18 CPU), поэтому времена — пессимистичная оценка, а не чистый максимум оборудования.**
Три прогона одного протокола (4 вызова на файл: 1 первый + 3 прогретых), каждый в новом контейнере:

| Прогон | Модель / параметры | Вес, MiB | RSS после загрузки, MiB | Пик RSS вызова, MiB | cgroup peak, MiB |
| --- | --- | --- | --- | --- | --- |
| `small` | small, fallback + conditioning (по умолчанию whisper) | 461 | 1219 | ≈1530 | ≈1566 |
| `turbo-default` | turbo, fallback + conditioning | 1543 | 3384 | ≈3740 | ≈4828 |
| `turbo-nofallback` | turbo, `temperature=0.0`, `condition_on_previous_text=False` | 1543 | 3384 | ≈3614 | ≈4815 |

Запуск процесса ≈0.7–0.9 с, загрузка модели (import + чтение) ≈5.4 с (при тёплом кэше ОС).

Выводы по замерам:

- Язык определялся верно на всех шести записях во всех трёх прогонах.
- У `small` на hy результат нестабилен (тексты различаются между повторами, времена 35–98 с):
  срабатывает температурный fallback. Смысловое совпадение на hy-30/hy-60 очень низкое.
- `turbo` на hy заметно лучше `small` (больше действий/имён/чисел совпало), на ru не хуже.
  С fallback у `turbo` hy-30 занимал ≈100 с и был нестабилен; `temperature=0.0` +

- Один вызов стоит ≈15–17 с на каждое 30-секундное окно (короткий файл тоже дополняется до окна):
  при загруженном CPU запись ≈60 с обрабатывается ≈30–58 с. hy-60 (55 с аудио) — 58 с только на STT.

## Выбор модели и параметров

- **Выбрано агентом по замерам: `turbo`** (`large-v3-turbo`), CPU fp32, `temperature=0.0`,
  `condition_on_previous_text=False`, автоопределение языка. По умолчанию в `Makefile`, CLI, Compose и
  `.env.example` (`WHISPER_MODEL=turbo`). `small` слабее на hy и нестабилен по времени; `medium`/`large-v3`
  не прогонялись: на этой CPU они заведомо медленнее `turbo` (≥ 2× по времени одного окна).
- Ресурсы worker: ≥ 4.8 GiB RAM (cgroup peak 4.8 GiB), ≈1.5 GiB на диске под веса, один процесс.
- **Ограничения (не скрывать):** качество hy низкое и человеком не подтверждено; на этой машине
  под нагрузкой STT для hy-60 ≈ 58 с, т.е. цель «задача на панели ≤ 60 с» для длинных hy-записей
  **не достигается** (на ru-60 ≈ 30 с — достижима). Замена на облачный STT не допускается; варианты —
  чистая машина/GPU (не проверялись), оценка владельцем и решение, принимать ли ограничение.
- Дата: 2026-10-22. Решение владельца: выбор делегирован («самостоятельно определи настройки»);
  подтверждения оценок и результата владельцем **нет**.

## Рекомендации для #14 (условные)

Механизмов очереди, lease и retry здесь нет; числа выведены из трёх прогонов шести образцов на
нагруженном хосте — это не p95 и не гарантия, верифицировать в #14.

- **STT timeout: 120 секунд** на запись ≤60 с — ≈2× измеренного максимума одного вызова
  (58.0 с, hy-60; повторы отличались на 1–2 с, т.к. декодирование детерминировано). Если worker
  получит более быстрый CPU — пересчитать по `results.json`.
- **Возврат Redis pending**: > 120 с (STT) + загрузка из Telegram/S3 + запись в БД + ACK; условно
  **≥ 180 секунд** либо явное продление владения. Конкретное значение подтвердить после замера
  I/O-этапов в #14.
- **Бюджет**: цель всего пути ≤ 60 с. STT один занимает до ≈58 с на длинной hy-записи,
  поэтому на этой конфигурации полный путь для неё **не укладывается**; для ru-60 STT ≈ 30 с
  оставляет ≈ 30 с на Telegram/S3/очередь/Tasks/панель — эти этапы ещё не измерены.
- Холодный старт worker: ≈ 0.7 с процесс + ≈ 5.4 с загрузка модели + первый вызов (≈ как прогретый);
  readiness — после загрузки в память.
